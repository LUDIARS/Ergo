# Ergo: プラグインのキュレーションとオーケストレーション、データテーブル

依頼 (2026-11-23, neco):
- 「Ergo はプラグインのキュレーションとオーケストレーションの仕組みなので、AI 授業からゲーム開発や CGLive、産業系のすべてに対応できるように設計」
- 「産業系は考えなくて良い」(2026-11-24): 産業系は対象から外す。用途はデータで足せる作りのままにし、産業系の定義は置かない。
- 「Ergo ファミリーのプラグインで調整されたデータアセットは専用のデータテーブルを持つので、それを元に Ergo で調整をする」

上位に置く方針。[ランチャーとリモート開発サーバ](2026-11-23-studio-launcher-and-devserver.md)・
[様式判定と Gen5 インテーク](2026-11-23-studio-gen5-intake.md) はこの方針の下の具体化。

## 1. Ergo の役割

Ergo は個々の機能を作り込む場所ではなく、プラグインを**選んで (キュレーション)**、プロジェクトに合わせて**組み合わせて動かす
(オーケストレーション)** 仕組み。機能はプラグイン (Ergo 内蔵・plugin pack・Ergo ファミリーのライブラリ) が持つ。

| 層 | 持つもの | 例 |
|---|---|---|
| Studio (ランチャー) | プロジェクトの選択・最近の記録・様式と用途の判定・インテーク・開発サーバの起動 | ergo_studio |
| オーケストレーション | 用途ごとのプラグイン構成 (どれを載せ、どの順で、どのデータテーブルにつなぐか) | プロフィールの `plugins` |
| プラグイン | 機能そのもの (表示・調整・生成・遠隔操作) | assets / play / tuning / particle / lookdev / lesson / ... |
| データテーブル | プラグインで調整したデータアセットの正本 | 下記 §3 |

## 2. 用途 (ドメイン) とプラグインの組 (キュレーション)

様式 (unity / cpp-ludiars / cpp-other / other。ビルドの形) とは別に、**用途**を持つ。用途は既定のプラグインの組を選ぶ。

| 用途 | 既定のプラグインの組 (例) | 既存の資産 |
|---|---|---|
| `lesson` (AI 授業) | lesson / play / tuning / log | Ergo の lesson プラグイン、Action Lab |
| `game` (ゲーム開発) | assets / play / tuning / particle / vfx / scene_editor / log / services / git + Gen5 インテーク | Amicii |
| `cglive` (CG ライブ) | lookdev / render_pipeline / pictor_perf / play (配信) / tuning | Pictor avatar-live、LiveDecorator |

- 用途の判定は様式と同じくランチャーで行い、プロフィールに `"domain"` があればそれを優先する (無ければ候補を出して人が選ぶ)。
- 用途の定義 (既定の組・インテークの点検項目) はデータ (`<studio home>/domains/*.json` と plugin pack 同梱) にし、Ergo のコードに
  用途ごとの分岐を書かない (新しい用途はファイルを足すだけ。Ergo CLAUDE.md の O 原則)。
- Gen5 インテーク (別紙) は `game` 用途の点検項目の組。他の用途はそれぞれの点検項目を持つ。

## 3. データテーブル

Ergo ファミリーのプラグインで調整したデータアセット (エフェクトのパラメータ、ルックの設定、バランス値、授業の課題値など) は、プラグインごとの**専用のデータテーブル**に持つ。Ergo はテーブルを元に調整する。

- **定義**: プラグインがテーブルの形 (列名・型・単位・範囲・既定値・説明) を宣言する (`IPluginDataTable`)。
  Ergo は形を解釈して調整画面を作る (テーブルごとに画面を書かない)。
- **置き場**: 実データはプロジェクトのリポジトリ (プロフィールの `tables` が場所を示す)。形式は行の追加・差分が読みやすいテキスト
  (JSON Lines か CSV。決めるのは実装時、両方は持たない)。
- **調整**: 動いているアプリ (ergo_bind) の値とテーブルの行を突き合わせ、編集・比較・版の保存/復元をする。今の tuning プラグインの
  版の仕組みはテーブルの版として一般化する。
- **生成**: AI 生成 (Concordia → Astra) はテーブルの形と各プロジェクトの仕様に従って行を作る (別紙のアセット生成)。
- **検証**: 形に合わない行 (型・範囲・必須欠け) は読み込み時に弾き、理由を出す。テストは形の宣言と検証の純粋関数で。

## 4. 段階への組み込み

- 段 1 (ランチャー): 様式に加えて用途 (`domain`) をプロフィールから読んで表示 (判定・候補提示は後段でよい)。
- 次段: 用途の定義ファイルとプラグインの組の適用 (開発サーバに載せるプラグインを用途で決める)。
- その次: `IPluginDataTable` とテーブルの調整画面。tuning の版を一般化。particle / lookdev から対応。
